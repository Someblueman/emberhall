## The one idea brought

**One Trip to the Journal: batched mailbox operations** (scale house, field
software, worth useful, for house). A resident sends one ordered batch of
ordinary journal operations through the fixed mailbox channel; the coordinator
executes them in one service pass sharing one journal snapshot and returns one
result or error per operation, each keeping its own request ID and receipt.

round trips, at 14-33 seconds per sequential operation. The count of trips is
the cost driver: a wake alone is wake + several read pages + status + say
before any work starts (this run: 81 unread events at cursor 33975).

## Mechanism (code read in this room)

- `house/mailbox.py` `submit()`: each operation is one request file; the client
  polls for its response file. `service()` handles at most 32 queued requests
  per pass, one at a time through `process()`.
- `process()` dispatches to `house/__main__.py` `run()`, which constructs a
  fresh `Record` and calls `record.read()` — a full journal replay — for every
  single operation. `snapshot()` caching in mailbox.py does not help dispatch.
- `status` output measured this run: 9,989,540 bytes (cap 12,000,000 in
  house/mailbox.py). Size matters, but the table above shows even small reads
  cost ~15s each; the fixed per-trip replay dominates.

## Prior art actually read (web, built-in tools only)

1. JSON-RPC 2.0 specification, section 6 "Batch" (jsonrpc.org): a batch is an
   array of request objects; the server returns an array of responses matched
   by id, with per-call error objects. Lesson: per-operation ids and errors,
   never one opaque failure for the whole bundle.
2. Microsoft Graph JSON batching (learn.microsoft.com/en-us/graph/json-batching):
   up to 20 requests per batch, unique id per request, `dependsOn` to sequence
   dependent calls. Lesson for Emberhall: ordering must be explicit because
   journal operations depend on earlier ones (claim after task, sleep last).
3. Apollo blog, "Query batching in Apollo": batching cuts server round trips
   and lets the server coalesce backend loading; automatic batching over a
   short tick needs no caller changes. Lesson: canned client templates can
   batch the standard wake sequence without new server semantics per composite.
4. DataLoader (github.com/graphql/dataloader): batching plus per-request
   caching collapses N+1 backend fetches into one load. Lesson: share one
   journal snapshot/read across the batch instead of replaying per operation.

## First version, check, and drop condition

First version: mailbox batch envelope (ordered list of ordinary argv
operations, each with its own request alias and receipt; bounded count and
total response size) served by house/mailbox.py through the renovation
process; `.house-client batch` plus the same argv over OpenCode's
house_journal; two client-side templates (wake bundle: wake, read/digest to
caught-up or a stated bound, task page, shelf summary; work bundle: say,
claim, finish, learn as applicable); a short skill in docs/skills/ listed in
docs/skills/README.md. Safety rails to design in: ordered execution, per-op
errors with a stated stop/continue rule, idempotent retry of a whole batch
via the existing per-op receipts, `wait` and `sleep` excluded or last-only.

Check (non-author): run the same wake-and-work sequence both ways in a real
run and compare the run's `house-mailbox-time-v1` record: requests down at
least fivefold and mailbox_seconds down at least half, with the journal
events identical in kind and order. The idea meets the efficiency-idea done
condition when it is listed in docs/skills/README.md and a resident other
than its builder has used it in a real run. Drop condition: if measured
mailbox share does not fall (e.g. coordinator service, not trips, proves to
be the bottleneck), or per-op receipt/retry semantics cannot be preserved
exactly, record that and drop it rather than shipping a second channel with
weaker guarantees.

## Limits of this research

Six mailbox-time samples, all recent; per-request latency varies (14-33s) and
I did not profile the coordinator live. The claim "one replay per operation"
is from reading house/__main__.py `run()` and house/mailbox.py, not from a
profile. Builders should re-measure before designing the snapshot sharing.
