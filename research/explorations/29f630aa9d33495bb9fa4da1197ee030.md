## Differentiation across jumps

The real problem: differentiating a numerical sum of samples can miss the
moving boundary contribution to the derivative of an integral. A language
with integrals and correct derivatives sounded promising, but it is not a new
language idea:

- [Potto, published paper record](https://dspace.mit.edu/entities/publication/65804cb1-7397-4224-880f-86bcfa1a033e)
  states the problem and its first-order, compositional language solution.
- [Potto, authors' 2023 workshop paper](https://differentiable.xyz/papers-2023/paper_55.pdf),
  read through its semantics discussion and conclusion, explains separate
  compilation, diffeomorphic conditions, the interior/boundary distinction,
  and its rendering comparison. This is an earlier version, not a substitute
  for the final paper's complete proof. The final PDF download returned 429.
- [Potto's implementation](https://github.com/divicomp/potto) gives an actual
  Python interface, the moving-step example, and reproducible case studies.
- [Teg](https://github.com/ChezJrk/Teg) already expresses integration and
  differentiation and includes that same step example. Its paper download
  exceeded the reader's size limit; I did not claim to read that full PDF.
- [A-delta](https://github.com/yyuting/Adelta) already supplies a discontinuous
  shader language, three backends, and one- and three-dimensional examples.
  Its different numerical treatment must not be advertised as exact symbolic
  integration. I read its README, not an executed implementation.
- [GradBench](https://github.com/gradbench/gradbench) already provides a
  cross-language derivative benchmark protocol, validation and nightly results.
  Its [listed evaluations](https://github.com/gradbench/gradbench/tree/main/evals)
  include ODE, particle and saddle problems. The directory listing alone does
  not establish what every evaluator tests.

An exact family of piecewise-polynomial integral/gradient cases might still
help researchers. I did not establish which cases are absent from the current
Teg/Potto tests or GradBench coverage: several test-tree reads failed. A new
benchmark deserves a concrete missing failure boundary and independent
expected answers, not the claim that current systems have no tests. No
performance or correctness comparison of those tools was run. I therefore
withheld both the new-language pitch and the benchmark pitch.

## Reversible programs and temporary values

The real question: can a programmer move one step backward across control flow
and a temporary variable's creation/deletion without storing every past state?
Existing work substantially narrows any honest proposal:

- [Sparcl, Journal of Functional Programming](https://www.cambridge.org/core/journals/journal-of-functional-programming/article/sparcl-a-language-for-partially-invertible-computation/809BDECF87B3748ED960FEFD42498BBE)
  presents a linear type discipline, an implementation and Agda proofs, plus
  tree and compression examples. A language merely combining ordinary and
  invertible computation would repeat this established idea.
- [Lanese and Vidal, A Reversible Semantics for Janus](https://arxiv.org/html/2602.16913v1)
  supplies the much closer predecessor: labelled control flow, two program
  positions, an active control stack, forward/backward rules, and a Loop Lemma
  on reachable configurations. I read the syntax, rules, proof discussion and
  future-work section. Procedures in this model have no parameters or local
  variables; extending it to local variables and stacks is explicitly future
  work. Thus a native stepper for that extension is a possible research lead,
  not a new discovery of reversible programming.
- [Jana's tutorial](https://github.com/kirkedal/Jana-JanusInterp/blob/master/Tutorial.md)
  already documents local/delocal, ancillas, stacks, call/uncall and several
  integer representations. Its [repository](https://github.com/kirkedal/Jana-JanusInterp)
  is an actual interpreter. Several source/manual tree reads failed, so I did
  not establish its exact interactive stepping behaviour.
- [Yokoyama, Reversible Computation and Reversible Programming Languages](https://people.cs.rutgers.edu/~uli/cs516/spring2020/readings/ReversibleComputing-TheoreticalCompSci2010.pdf),
  especially pages 4-8, already defines local allocation/deallocation,
  shadowing, exit-value checks and inverse calls. A proof that local/delocal is
  reversible at block boundaries would add nothing by itself.
- [Kuroda and Yuen, concurrent Janus](https://www.jstage.jst.go.jp/article/ipsjjip/34/0/34_444/_article/-char/en)
  describes a 2026 implementation with a reversible intermediate language,
  dependency records and nested memory management. I read its abstract; the
  PDF fetch timed out. This is not evidence that its detailed semantics are
  equivalent to the history-free sequential model.

A serious follow-up would first compare the latest Janus implementations and
papers at the transition level. It would state exact scope, shadowing and
recursive-call rules, prove individual steps invert on reachable states, and
show equivalence to the existing block semantics. A debugger would execute a
real source program from the command line; a web animation or reversing a
saved trace would not answer the question. I have not completed that comparison
or shown why this extension alone earns a multi-day project. No claim of a
new theorem, first debugger, universal reversibility or physical energy
savings is made.
