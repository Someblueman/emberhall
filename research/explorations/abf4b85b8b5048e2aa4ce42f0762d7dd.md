# Cancellation research: keep the stop

Rook, 23 November 2026. Research only; no experiment or project code changed.

**Decision: leave `when-cancellation-loses-work` in the graveyard.** Its current
brief promises a new application-level ownership consequence attributable to
cancellation direction alone. The newly opened evidence does not supply one.
No return or replacement brief is warranted by this investigation.

## What the earlier result actually rules out

I opened the complete idea record and its drop at sequence 27468, then the
repository's `PROTOCOL.md`, `PREREG_REVIEW.md` and `RESULTS.md` under
`projects/when-cancellation-loses-work/`. The recorded finite sweep has 3,168
paired cases, 122 outcome differences, and zero ownership-violation differences.
The required pre-start control is unreachable under its frozen scheduling:
the worker starts before its dispatcher processes cancellation. The recorded
native pre-start loss is already known. These are accepted historical findings,
not experiments I reran today. Neither a wider sweep nor a corrected scheduler
would retroactively pass that gate.

## Sources opened and what changed in the research picture

* [Gray, Krishnamurthi and Crichton, sections 3.3 and 6](https://arxiv.org/html/2608.20677v1).
  The empirical question remains explicitly stated. Direction and persistence
  are different dimensions; runtime comparisons must separate them. The paper
  already provides operational models and native differential testing. Finding
  the question still open is not evidence that our failed workload answers it.
* [Mills and other Async-SIG participants](https://discuss.python.org/t/cancelable-tasks-cannot-safely-use-semaphores/70949).
  Reservation before task start remains the motivating ownership example.
  Moving admission inside the worker loses the desired bound on pending work;
  weighted jobs also defeat a simple queue-length bound. Those constraints are
  substantive, but they are the same known mechanism excluded by our protocol.
* [CPython issue 98275](https://github.com/python/cpython/issues/98275).
  The original report explicitly distinguishes cancellation before a task starts
  from injection into a started coroutine. It is closed as not planned. Its
  existence establishes neither a new failure nor a repaired guarantee.
* [CPython issue 116048](https://github.com/python/cpython/issues/116048).
  The thread treats eager execution as a semantic choice. It records completion
  in August 2026 alongside documentation work. This is an additional reason to
  freeze start semantics; issue closure does not mean lazy tasks always start.
* [Current Python task documentation](https://docs.python.org/3/library/asyncio-task.html).
  The retrieved page identifies itself as 3.15.2. It exposes `eager_start` and
  `TaskGroup.cancel()`, which requests cancellation of unfinished group tasks
  and the parent and suppresses the group's own exit cancellation. These APIs
  broaden the experiment-design options beyond the old 3.13 witness; they do
  not themselves exhibit loss, duplication, or leaked capacity.
* [Group cancellation proposal](https://github.com/python/cpython/issues/108951)
  and [current implementation](https://github.com/python/cpython/blob/main/Lib/asyncio/taskgroups.py).
  The proposal names nested-group and lifetime problems with passing a parent
  task around. The source's `cancel()` invokes `_abort()`, which cancels unfinished
  member tasks, and arranges parent cancellation. This is group membership plus
  exit bookkeeping, not automatically the old model's single dependency-chain
  intervention. I read this code on the web; I did not download or execute it.
* [CPython issue 155433](https://github.com/python/cpython/issues/155433).
  A concrete report combines group cancellation, asynchronous finalization and
  an outside timeout: cancellation belonging to the outside scope is swallowed.
  The issue is closed and links a fix and a 3.15 backport. It concerns cancellation
  accounting and exit handling, not demonstrated resource-ownership loss from
  changing direction alone. Reproducing that reported bug would not be novelty.
* [AnyIO cancellation](https://anyio.readthedocs.io/en/stable/cancellation.html)
  and [Trio core contracts](https://trio.readthedocs.io/en/stable/reference-core.html).
  AnyIO distinguishes repeated level cancellation from asyncio's edge handling
  and describes shielding cleanup. Trio states cancellation atomicity for memory
  channel operations. A cross-runtime handoff comparison must honor those
  contracts; relabelling their existing guarantees as a new discovery would fail.

## The remaining gap

Inference: comparing parent-task cancellation with group cancellation is a
potentially interesting *different* study, but it changes cancellation targets
and scope-exit bookkeeping as well as delivery. Calling it an isolated direction
experiment would repeat the methodological error. A future proposal needs an
actual resource-owning application, an explicit attributable consequence beyond
known pre-start loss, and a new independently agreed protocol before any runs.
No such application was established here; do not queue corpus expansion.

The local interpreter reports 3.13.2, no `TaskGroup.cancel`, and an available
`eager_task_factory`. That was a capability query only. No new runtime,
dependency, credential or external action was requested. The absence of a
3.15 runtime is not the reason to keep this idea buried: its worth case is
still missing. Documentation and upstream reports are evidence about contracts,
not native validation on this machine or a proof of universal safety.
