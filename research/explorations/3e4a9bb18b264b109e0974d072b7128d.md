marked as such. The sources were opened with the built-in web reader on

1. [azmeuk, Stack Overflow question 52755140](https://stackoverflow.com/questions/52755140/three-way-dictionary-deep-merge-in-python),
   asked 11 October 2018, explicitly requests recursive merging of two
   dictionaries against their common predecessor, including additions,
   deletions and exceptions for conflicting changes. The question says:
   “knowing a common previous state C of both dictionaries.” This is direct
   evidence for ancestor-aware merging. Answers exist; later comments identify
   missing-versus-`None` and unhashable-value problems in one proposed answer.
   Neither the age nor the existence of the question proves current broad demand.
2. [patrickwolf, DeepDiff issue 552](https://github.com/qlustered/deepdiff/issues/552),
   opened 13 June 2025, asks for a convenient recursive combination of **two**
   dictionaries instead of a multi-step diff/patch workflow. It does not ask
   for a common ancestor or establish three-way conflict semantics. A subsequent
   comment advertises a helper that can match list records by an identity key;
   that is an untested claim by its author, not a capability verified here.
3. [netllama, dictdiffer issue 131](https://github.com/inveniosoftware/dictdiffer/issues/131),
   opened 26 November 2019, reports trouble comparing lists of dictionaries
   when their order or length changes. The supplied example is routing data.
   This supports the relevance of record matching, not a direct request for
   three-way merging or proof of a defect in every current version.
4. [Sophia Willows, Avoid JSON file merge conflicts](https://sophiabits.com/blog/avoid-json-file-merge-conflicts),
   dated 18 July 2023, describes frequent end-of-object merge conflicts and
   discusses JSON5, a custom merge driver and a trailing sentinel member.
   This is practical context for Git friction, not evidence that those
   alternatives are insufficient or that this proposed library is required.

The strongest direct request is the Stack Overflow question. The other sources
describe related needs. Together they do not establish a large audience, novel
algorithms, or superiority to existing tools. A future selection would need to
defend the intended users and the value of a complete ancestor-aware API.

## Proposed work retained from the original note

The candidate is a zero-dependency Python library (`jsonmerge3`) with a real
importing example and `python3 -m jsonmerge3` command, plus an optional Git merge
driver. This is a proposed dependency constraint, not a demonstrated advantage
or a claim that the package already exists.

The intended `merge3(base, ours, theirs)` would distinguish unchanged values,
one-sided additions, edits and deletions, equal changes on both sides, and
conflicting edits or delete/modify pairs. Missing members must be distinct from
JSON `null`. Arrays would need explicit policies: identity-keyed records,
ordered sequences, or order-independent unique values. Duplicate identities,
incompatible reordering and incompatible type changes need defined outcomes;
the original list of algorithms is a design proposal, not a correctness proof.

A proposed result would carry a value, a clean/conflicted status and structured
conflicts, with configurable resolution. Real acceptance would include an
importing program and temporary-Git-repository exercises of merge and
cherry-pick. No implementation or such acceptance run was made in this repair.

### JSON Pointer correction

[RFC 6901, sections 3–4](https://www.rfc-editor.org/rfc/rfc6901.txt) distinguishes
object-member names from zero-based array indices. For the document
`{"users":[{"id":42,"role":"reader"}]}`, `/users/0/role` resolves to `reader`.
`/users/id=42/role` is syntactically a pointer string, but **does not resolve**:
`users` is an array, and `id=42` is not an array index. It is not a keyed lookup
defined by RFC 6901. It could resolve in a different document where `users` is
an object with a member literally named `id=42`.

Identity matching therefore belongs in separately typed selector metadata.
For example, a conflict may identify `id` value `42` and separately record
`ours_path: /users/0/role` and `theirs_path: /users/2/role`, each bound to its
own input document. A deletion has no resolvable path in the deleting input;
report the base location and explicit absence instead. Do not promise one
numeric pointer remains stable across reordered inputs. Escape literal `~`
and `/` in object-member tokens as `~0` and `~1`.
