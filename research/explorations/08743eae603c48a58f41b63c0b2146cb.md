## Numerical uncertainty: substantial existing coverage

The need is real: measurement error, finite precision and branching can undermine
numerical results. [Darulova's thesis abstract](https://infoscience.epfl.ch/entities/publication/ce5ee3b0-5788-4d29-8532-ee0fdb93f57c)
explicitly identifies those problems and already describes a real-valued language
with error annotations and a verifying precision-selecting compiler. I opened
that abstract, not the thesis in full. [On Sound Compilation of Reals](https://arxiv.org/abs/1309.2511)
is another opened primary abstract describing this approach.

[Daisy's documentation](https://raw.githubusercontent.com/malyzajko/daisy/master/doc/documentation.md)
provides an actual input program, error contracts, interval/affine/solver-based
analyses, mixed precision and generated C or Scala. That directly defeats a
proposal whose distinguishing feature is merely writing an error budget beside
a numerical program. [Measurements.jl's current usage documentation](https://juliaphysics.github.io/Measurements.jl/dev/usage/)
already retains functional correlations, accepts covariance matrices and works
with units. Its warning that copying printed values creates independent inputs
is a genuine boundary, but not evidence that a new language is the right remedy.
Its derivative-based uncertainty propagation must not be confused with Daisy's
sound roundoff bounds.

The adjacent idea of separating probability from unknown probability also has
close prior work: [Imp's published package description](https://hackage-content.haskell.org/package/imp-ppl)
describes a discrete language with Knightian uncertainty and lower/upper
probabilities. [Caesar's own overview](https://www.caesarverifier.org/) describes
HeyVL, nondeterminism, quantitative proofs and unbounded loops. These are
published descriptions, not independently reproduced execution results.

Decision: do not publish a new numerical language on these broad claims.
A return needs a particular scientific program and a precise missing guarantee,
with the closest existing analysis applied to the same program.

## Edits that retain source information: not a new basic language idea

[Retentive Lenses](https://arxiv.org/html/2001.02031v2), especially definitions
3.2–3.7, already adds explicit correspondence links and a retention law, and
states that its tree-transformation language generates retentive lenses. Ordinary
round-trip laws alone do not promise local retention. Conversely, the retention
law depends on supplied links: the paper explicitly exhibits a vacuous empty-link
construction. That is a limitation to understand, not a counterexample to its
claimed law.

I considered requiring explicit permission for every discarded comment or source
fragment. I did not establish that this is a new semantics or a compelling program
rather than a stronger link policy. The opened abstract of [multiary delta
lenses](https://arxiv.org/abs/1911.11302) also prevents treating multiple views and
amended updates as unexplored. [Cambria](https://www.inkandswitch.com/cambria/)
already demonstrates executable schema transformations and collaboration across
versions. Neither source proves that all possible edit-retention languages are
redundant. The narrower conclusion is that this screen lacks a discriminating
program and comparison.

## Live workflow migration: an unresolved lead, not an accepted candidate

[Transparent Continuation Checkpointing, sections 11–12](https://trigora.dev/research/whitepaper/)
distinguishes recovery under the original artifact from moving a saved continuation
to new code. The latter is explicitly future work. It also disclaims universal
exactly-once external effects. This is a concrete open implementation boundary;
checkpointing alone must not be advertised as solving migration.

But typed live updates and state transformers are old:
[Proteus, introduction and update semantics](https://www.cl.cam.ac.uk/~pes20/update-popl-2005.pdf)
already gives type-safe dynamic updates, including active functions. Its current
activation continues old code; new calls use the replacement. That differs from
rewriting a suspended continuation, but does not establish originality for doing
so. [Nulang's workflow overview](https://nulang.org/workflows/overview/) is another
opened language-level durable-workflow description, not a tested implementation.
[The 2026 upgrade-risk paper](https://arxiv.org/html/2607.13617), including section
11, already treats replay compatibility and migration risk; it expressly limits
claims about behavioral desirability, unseen paths and unobserved channels.

A possible future question is whether explicit, typed transformations of waiting
continuations can preserve pending-effect identities while changing local state
and future control flow. This screen supplies neither such a calculus nor a
comparison proving an advantage over established update mechanisms. A credible
return needs one concrete old/new workflow pair, an exact crash and effect model,
a rejection example that existing tools miss, and a feasible first-stage theorem.
Do not expand that into arbitrary safe updates or exactly-once effects.
