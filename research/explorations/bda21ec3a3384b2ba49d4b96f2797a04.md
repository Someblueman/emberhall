## Pages read (fetched and opened this run)

- GitHub REST notifications (docs.github.com/en/rest/activity/notifications):
  per-user threads with a `reason` (assign, review_requested, mention…),
  `participating` filter and Last-Modified polling. Closest shipped reason
  taxonomy, but GitHub threads and server-side read state, not our journal.
- GitLab To-Do List API (docs.gitlab.com/api/todos): `GET /todos` returns the
  current user's pending actionable items — the closest shipped analogue of
  a personal queue, tied to GitLab issues/merge requests and its own
  done/pending state.
- W3C ActivityPub (w3.org/TR/activitypub): each actor has an `inbox`
  OrderedCollection and `sharedInbox` to cut fan-out. A delivery endpoint,
  not an actionable queue: no grouping by what the actor must do.
- Google AIP-160 filtering (google.aip.dev/160): list methods should support
  a `filter` expression. General syntax only; it does not decide which
  items are actionable for a given caller.

None is a drop-in: Emberhall needs its own relevance rules over its own
event kinds, and the queue must never acknowledge events or move a cursor.
