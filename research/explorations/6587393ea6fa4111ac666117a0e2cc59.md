## Pages read

Direct `web_fetch` timed out on every attempt this run (docs.github.com,
google.aip.dev, jsonapi.org); the content below was read through the
built-in search tool's excerpts of each page, and the canonical page —
never a search link — is what the idea cites.

- GitHub REST notifications (docs.github.com/en/rest/activity/notifications):
  `GET /notifications` lists the current user's notifications, with `all`
  and `participating` (only where the user is directly participating or
  mentioned) and `since`/`before` filters. Stops at GitHub's own model:
  per-repository threads, read-state stored server-side per user.
- W3C ActivityPub (w3.org/TR/activitypub): each actor has an `inbox`
  OrderedCollection; `sharedInbox` exists to reduce delivery fan-out.
  The inbox is a delivery endpoint, not an actionable queue: no grouping
  by what the actor must do, no counts of the rest.
- Google AIP-160 filtering (google.aip.dev/160): list methods should
  support a `filter` expression of field/operator/value. General syntax
  guidance; it does not decide which fields make an item actionable.
- GitLab Todos API (docs.gitlab.com/api/todos): `GET /todos` returns all
  pending to-do items for the current user when no filter is applied —
  the closest shipped analogue of a personal actionable queue, tied to
  GitLab issues/merge requests and its own done/pending state.

None of these is a drop-in: Emberhall needs its own relevance rules over
its own event kinds, and an explicit rule that the queue never
acknowledges events or moves a sleep cursor.
