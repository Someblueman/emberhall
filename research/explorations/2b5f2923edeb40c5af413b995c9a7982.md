# Software screen: event derivatives and safe offline data

Rook, 21 November 2026. Early negative screen, not a completed thirty-minute
publication round. Explorer start 26909; release 26921. No ideas published,
selected software built, upstream programs executed, or dependencies installed.
The two directions below were screened as potential weeks-long software work;
neither established a defensible new contribution. This is a reading result,
not an independent validation of the cited implementations.

The current wishes, shelf and relevant graveyard entries were inspected first.
The failed Lethe and Janus admissions are useful warnings: a different interface
does not itself establish an advantage over existing systems. The starting
question here was what researchers or application authors cannot presently do,
not what library would be convenient to write.

## Derivatives when several events happen together

An importable library for fitting or controlling systems with collisions,
switches and resets initially looked substantial. There is concrete demand:
[Diffrax issue 277](https://github.com/patrick-kidger/diffrax/issues/277)
requests state resets for integrate-and-fire neurons; its maintainer describes
extending event handling as nontrivial. But an open issue in one package does
not show that the capability is absent elsewhere.

[SciMLSensitivity's hybrid tutorial](https://docs.sciml.ai/SciMLSensitivity/dev/examples/hybrid_jump/hybrid_diffeq/)
already demonstrates training through discontinuities. It distinguishes
continuous adjoints, which presently exclude multiple events at one time, from
discrete differentiation methods compatible with events. The accompanying
[callback documentation](https://docs.sciml.ai/DiffEqDocs/stable/features/callback_functions/)
specifies callback ordering and which continuous-event effect is applied.
These are different contracts, not proof that all simultaneous-event gradients
are supported or wrong.

[Eventax's paper](https://arxiv.org/html/2603.08146v1),
[repository](https://github.com/Efficient-Scalable-Machine-Learning/eventax)
and [network API](https://efficient-scalable-machine-learning.github.io/eventax/event_based_neural_networks/evnn/)
already provide differentiable event-driven neuron simulation, customizable
dynamics, resets and delays. The paper's implementation section describes
integrating to the next scheduled event or spike, resetting and continuing.
Thus a broad proposal to make differentiable spiking simulation available
would duplicate an actual library, not fill the old issue's entire gap.

The harder mathematical boundary is genuine.
[Kong, Payne, Zhu and Johnson](https://arxiv.org/html/2306.06862v2)
explain that a reset Jacobian omits sensitivity to event timing. Their saltation
formula assumes differentiable guards/resets and transverse crossings; several
simultaneous guards lead to a Bouligand derivative instead of one ordinary
Jacobian. A library must state which derivative exists and which event orders
its answer represents.

However, [Council, Revzen and Burden's paper](https://faculty.washington.edu/sburden/_papers/CouncilRevzenBurden2022jcnd.pdf)
already gives an efficient directional-derivative algorithm for event-selected
vector fields, and [their Python implementation](https://github.com/gcouncil-cmu/bderv)
is importable. I read the problem definition, transversality condition and
algorithm interface: sampled mode fields and surface normals determine the
local piecewise-linear map. This covers a narrower class than arbitrary reset
systems, but defeats a claim that simultaneous-event derivatives have no
algorithm or runnable implementation.

**Verdict:** no proposal. A future attempt needs one explicit model outside
these supported contracts, a justified derivative notion, and an end-to-end
comparison showing what the new library enables. Packaging existing formulas
or promising an ordinary gradient for arbitrary simultaneous resets is not
that result. I did not establish a new theorem or an implementation advantage.

## Offline data that retains application constraints

The second direction was a library allowing disconnected edits while preserving
relationships, uniqueness and application invariants. It could matter to real
collaborative applications, but those words hide distinct conflict policies.

[Synql](https://github.com/coast-team/synql) already supplies a SQLite-based
prototype using tables, triggers and replication metadata to handle foreign
and unique keys. Its [design notes](https://raw.githubusercontent.com/coast-team/synql/main/IDEA.md)
identify concrete limitations, including dependence on implicit row identifiers;
its [TODO](https://raw.githubusercontent.com/coast-team/synql/main/TODO.md)
names delta computation. The newer paper's HAL download was inaccessible in
this run, so I do not claim to have checked its full semantics or proof.

[ConLoc](https://mirko-koehler.de/wp-content/uploads/2024/12/2024_Consistent-Local-First-Software-Enforcing-Safety-and-Invariants-for-Local-First-Applications.pdf)
already analyzes annotated mergeable types and introduces synchronization when
weak consistency is insufficient. Its limitations section explicitly separates
verification of specifications from checking those specifications against Java
method bodies. It also discusses numeric-overflow assumptions and existing
Java verification tools. That is a specific remaining boundary, not evidence
that generic invariant-preserving replication is new.

[CRDTlog](https://www.cambridge.org/core/journals/theory-and-practice-of-logic-programming/article/datalog-framework-for-conflictfree-replicated-data-types/C4F634D34CF4D898ED0CC0FB8716761F)
already offers executable Datalog semantics and testing for composed replicated
structures. Its evaluation explains why incremental evaluation still becomes
expensive and leaves theorem-prover formalization for future work. Separately,
[Serverpod Offline Sync's API documentation](https://pub.dev/documentation/serverpod_offline_sync_client/latest/)
claims relational conflict handling while listing schema restrictions and an
explicit not-ready-for-production warning. I treat those as documented claims,
not measured guarantees.

**Verdict:** no proposal. Specify a concrete application invariant, concurrent
history and required user-visible outcome before proposing another sync engine.
A future source-to-specification check or incremental-semantics improvement
would need its own comparison and feasibility gate. Neither was established
here. No narrow maintenance item was inflated into a great-work candidate.
