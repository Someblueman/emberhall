## 1. `review-skein` — Skein: a code review you can carry across an air gap

### Proposal

A local-first review press: combine a static, keyboard-accessible diff and
anchored comments with the exact Git bundle under review. An occasional
reviewer receives one portable packet, inspects and annotates it without a
forge, daemon or account, and returns another packet.

### What the alternatives establish

- [Git bundle](https://git-scm.com/docs/git-bundle) officially supports moving
  refs and objects without an active server, including full and incremental
  transfers. `verify` checks bundle validity and prerequisites; it does not
  establish authorship or include uncommitted/index/stash/configuration state.
- [Git notes](https://git-scm.com/docs/git-notes) attaches additional blobs to
  objects without changing those objects and histories notes refs with commits.
  This is a useful precedent, not an implementation requirement.
- [Gerrit NoteDb](https://gerrit-review.googlesource.com/Documentation/note-db.html)
  stores patch sets and review metadata in Git, with an auditable history.
- [Radicle's user guide](https://radicle.dev/guides/user) already offers
  local-first issues, patches and comments, cryptographic identities and later
  network synchronization. Its [protocol guide](https://radicle.dev/guides/protocol)
  explains Git-backed collaborative objects. This is a strong alternative, not
  an empty niche. The protocol page also has a dated warning and a removed
  transport-security section; Skein must not borrow a security claim from it.

### Narrow missing value and uncertainty

Skein is **not another network or forge**. Its proposed value is a
zero-service, human-readable exchange object for the person who cannot or does
not want to run one: a static accessible review plus the matching Git bytes,
with comments and history that can be archived beside a release. Possible uses
are air-gapped teams, classrooms, volunteers exchanging drives and retainers
leaving review evidence with a handoff.

Radicle already covers offline patches with signed identities; Gerrit covers
rich patch sets and NoteDb history. Skein should lose unless an actual exported
packet is materially simpler for that occasional-reviewer workflow. Hashing
binds bytes, not people. Confidentiality, signed identities, automatic merge,
trust in test evidence and adoption remain unproven. Large/binary diffs,
rewritten patch sets and concurrent comment merges may make the simple packet
less attractive than existing tools.

### Canonical first step

After selection, build only `projects/review-skein/` milestone 1: a stdlib CLI
that reads two named committed refs in a real Git fixture repo and writes a
versioned review packet containing immutable base/head IDs, a static escaped
side-by-side diff, and an ordinary full Git bundle; reject uncommitted or
ambiguous refs, unsafe paths, binaries and oversized files honestly. Add a
small comment model anchored to commit/path/old-or-new line with an explicit
orphan-on-rebase state, JSON roundtrip and tests for renamed files, Unicode,
tabs, duplicate lines, missing anchors and bundle verification/reproduction. A
non-author exports a packet from one fixture, opens it without network and
records one comment before later milestones add merging. No authentication,
merge/apply or live service in the first milestone.

### Suggested later milestones (plans, not started work)

1. **Packet and anchors (7 days):** the canonical first step above.
2. **Use the packet (10 days):** keyboard and screen-reader-oriented review,
   comment/resolution editing, accessibility and phone/desktop independent try.
3. **Two reviewers (14 days):** deterministic append/merge, divergent and orphan
   comments, revised patches, non-author two-repository exchange trial.
4. **Introduce Skein honestly (10 days):** examples, fixture corpora, recovery,
   documentation and an outside-user recipe; measure whether zero-service
   exchange really is easier than `git bundle`, Gerrit or Radicle for this case.

## 2. `chorus-archive` — Chorus: an oral-history box with consent in the package

### Proposal

A private, local-first studio for families and small history groups: preserve
original recordings, attach consent and timecoded chapters, then export a
playable static archive whose media and transcript share permissions are
inspectable and travel together.

### What the alternatives establish

- [StoryCorps recording guide](https://support.storycorps.org/help-center/how-do-i-record-an-interview-with-the-storycorps-app)
  documents guided recording, custom questions, drafts, privacy settings and
  publishing to its archive. Its [audio export guide](https://support.storycorps.org/help-center/exporting-your-interview-audio-from-the-storycorps-app)
  explicitly supports exporting draft audio through the app or USB. Chorus does
  not claim that recording or audio backup is missing there.
- [OHMS](https://www.oralhistoryonline.org/help/faq/) already connects indexed
  or synchronized transcripts to online media, exports XML and supports import
  for editing. Its FAQ says OHMS is not a repository: media is hosted elsewhere
  and linked. That is an architectural comparison, not a quality judgment.
- [Boston Public Library's consent guide](https://guides.bpl.org/OralHistory/consent)
  says informed consent covers purpose, possible uses/storage, benefits/risks,
  and may be recorded or written. Its [preservation guide](https://guides.bpl.org/OralHistory/preservation)
  recommends keeping originals, forms and documentation together, described
  and backed up in multiple locations, with privacy and ownership considered.
- The [Library of Congress cultural-documentation index](https://maint.loc.gov/folklife/edresources/ed-trainingdocuments.html)
  appears to cover planning, ethics, field notes, interview logs and release
  forms. Direct fetch failed, so this is a lead for builders, not a verified
  quotation or detailed claim.

### Narrow missing value and uncertainty

Chorus is not just a recorder or transcription box. Its proposed object is a
**completely local interview package**: the original bytes, consent record,
chapters and segment-level withholding decisions stay inspectable together;
the share export is a static playable archive a family or small museum can copy
without deploying an OHMS viewer or putting media on a server. Withheld material
is omitted from share bytes, not merely visually hidden, while the private
project retains a careful omissions inventory.

Consent records document a choice; they do not provide legal compliance,
anonymity or guaranteed withdrawal from copies already shared. Long interviews
and browser storage quotas may require a filesystem-backed shell. Timecoding is
real labor. No evidence says families will prefer this to StoryCorps, or that
OHMS cannot satisfy an archive's needs. A first field trial must test actual
narrator comprehension and playback, not just manifest arithmetic.

### Canonical first step

After selection, build only `projects/chorus-archive/` milestone 1: import one
small user-supplied WAV with title, participants, a consent note and several
manually timecoded transcript chapters; keep the original unchanged. Export a
deterministic private project plus a share folder containing static HTML,
copied permitted media, WebVTT/JSON/plain transcript, per-file SHA-256 manifest,
and a non-sensitive omissions inventory. Any narrator/session lacking an
explicit share flag, and every restricted segment, must be absent from the
share payload rather than merely hidden in its UI. Tests cover HTML escaping,
unsafe paths, invalid/overlapping timestamps, duplicate IDs, missing/changed
media, whole-interview withholding and import/export roundtrip. A non-author
opens the result without network, plays a supplied fixture, checks keyboard
transcript navigation and verifies restricted bytes are absent. No automatic
transcription, preservation-quality claim or legal-compliance claim.

### Suggested later milestones (plans, not started work)

1. **Consent-bound package (7 days):** the canonical first step above.
2. **Chapter workshop (10 days):** usable timecoded editing, rehearsal and
   correction with imported media, autosave/recovery and accessibility checks.
3. **Collection and preservation (14 days):** multiple interviews, search,
   portable collection export/import, integrity review and backup documentation.
4. **Field trial and recording choice (14 days):** optional capture with an
   import fallback, independent narrator/interviewer try, explicit review of
   omissions and archive usability before any recommendation.
