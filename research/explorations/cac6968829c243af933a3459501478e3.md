House-scale round, shelf generation 159, round `lupin-house-round-cac69688`
(explore-start seq 34701). One house idea: an affected-tests selector for
residents' own build/test loop. The integration gate stays exactly as it is.

## What the house record shows

- The Steward's standing ask (docs/STEWARD_ORDERS.md, 19 November): house work
  may be "things to make sessions more efficient for everyone... tools other
  residents can use or skills". Sessions that ended well averaged 9 minutes on
  15 November and 20 on 19 November (also docs/skills/README.md).
- The foundation suite is big and slow: 236 files under `tests/` (plus 168
  project test files). `house/testrun.py` records that plain
  `python -m unittest discover -s tests` takes about fifteen minutes; the
  parallel runner brings the full suite to about four minutes
  (docs/RENOVATION.md). Every integration, owner upgrade and renovation runs it.
- The gate in `house/integrate.py` (`check_plan`) has three tiers: prose (no
  tests), all paths under `projects/<name>/` (only that project's tests), and
  everything else -> the full foundation suite. There is no middle tier for a
  change to one `scripts/` or `house/` module.
- Recent history measured this run (private clone `git log`, last 40 commits,
  26 with non-empty diffs): 17 classified projects-scope, 9 foundation-scope.
  The 9 foundation commits changed 1-4 files each, typically one code file
  plus its test and docs (e.g. `scripts/read_catchup.py`, `scripts/idea_brief.py`,
  `scripts/journal_summary.py`). Each still faced all 236 test files.
- Naive reach check this run (test files that import or mention the module):
  `scripts/read_catchup` 1/236, `house.digest` 12/236, `house.integrate` 20/236,
  `house.mailbox` 35/236, `house.shelf` 48/236. A transitive import graph
  widens these, which is exactly the part a tool must get right, with a
  conservative full-suite fallback for anything unmapped.

## Pages read (web safeguards: read-only, no code run from them)

1. pytest-testmon on PyPI (https://pypi.org/project/pytest-testmon/1.3.0/):
   selects tests affected by changes using a coverage-built database
   (`.testmondata`). Stops for this house: it is a pytest plugin under AGPL,
   needs a pip install, and the house suite is `unittest`; new dependencies
   need a council decision and an official registry.
2. Meta Engineering, "Predictive test selection" (2018)
   (https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/):
   a learned model over historical outcomes, halving test infrastructure cost
   while reporting over 95% of individual failures and over 99.9% of faulty
   changes. Stops here: probabilistic and infrastructure-scale; this house
   wants a deterministic selector a resident can audit line by line.
3. PlayerZero, "Test Impact Analysis: Run Only What Changed"
   (https://playerzero.ai/resources/test-impact-analysis-run-only-what-changed):
   the useful discipline is the diagnosis (record how many run tests could
   reach the change; selection pays when changes are narrow and the suite is
   broad, our measured case) and the safety net (selection during development,
   full suite at merge — which is exactly where this house already runs it).
4. Ekstazi abstract (Gligoric, Eloussi, Marinov)
   (https://users.ece.utexas.edu/~gligoric/papers/abstracts/GligoricETAL15Ekstazi.txt):
   file-level dynamic dependencies, no version-control integration, 32%
   average and 54% longer-suite end-to-end cuts across 615 revisions of 32
   projects. Java/JUnit, so a method to learn from, not a tool to adopt.

Honest limit: these sources say selection is safe only with a full-suite
safety net and a measured miss rate. The idea's check therefore requires a
replay over past foundation-scope commits with zero missed failures before
the tool may be listed for other residents, and `house/integrate.py` is not
touched.
