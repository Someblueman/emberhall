## Array interchange and ownership

The need is real: independent numerical libraries share memory through small
interfaces whose ownership rules matter. The [Arrow C interface](https://arrow.apache.org/docs/format/CDataInterface.html)
specifies release callbacks, relocation and moving child arrays. However,
[Arrow integration tests](https://arrow.apache.org/docs/format/Integration.html)
already compare producer/consumer pairs and can check leaks. The
[nanoarrow testing API](https://arrow.apache.org/nanoarrow/main/reference/testing.html)
already supplies shared test-data readers, writers and comparison helpers.
The [C# leak report](https://github.com/apache/arrow/issues/40898) documents an
actual failure caught by this ecosystem; it is closed, not evidence of a
currently unfixed bug. [Arrow fuzzing](https://arrow.apache.org/docs/developers/cpp/fuzzing.html)
also has existing targets and regression corpora.

I then examined DLPack rather than assuming Arrow's coverage transferred.
Its [Python specification](https://dmlc.github.io/dlpack/latest/python_spec.html)
and the [Array API interchange requirements](https://data-apis.org/array-api/latest/design_topics/data_interchange.html)
give concrete copy, device and lifetime obligations. The
[merged Array API test contribution](https://github.com/data-apis/array-api-tests/pull/433)
explicitly scoped its initial work to one library at a time. The
[current test source](https://raw.githubusercontent.com/data-apis/array-api-tests/master/array_api_tests/test_dlpack.py)
still contains TODOs for copy and device cases. But
[NumPy's own test source](https://raw.githubusercontent.com/numpy/numpy/main/numpy/_core/tests/test_dlpack.py)
already tests reference counts, destructor exceptions, strides, read-only
arrays and copying. A portable cross-library lifetime corpus remains a lead,
not an established missing capability. I did not demonstrate a failure missed
by the existing suites or justify a separate weeks-long project. Do not turn
the upstream TODOs into a claim that nobody tests ownership.

## Terminal accessibility and semantic adapters

[Accessibility of Command Line Interfaces](https://storage.googleapis.com/gweb-research2023-media/pubtools/6065.pdf)
reports studies with twelve developers and identifies unstructured output as
a barrier. That establishes a need, not an absence of implementations.
[Microsoft's terminal accessibility account](https://github.com/microsoft/terminal/blob/main/doc/terminal-a11y-2023.md)
describes existing work. [tui-a11y](https://docs.rs/tui-a11y/latest/tui_a11y/)
already exposes an application-declared tree through Linux accessibility APIs.
The [Ratatui discussion](https://github.com/ratatui/ratatui/issues/2610)
contains a reported Orca trial, limited to Linux; I did not reproduce it.

[Taria](https://y0sif.github.io/taria/) supplies semantic nodes and acknowledged
actions for agents. Its [protocol](https://github.com/y0sif/taria/blob/main/docs/protocol.md)
explicitly lacks exported conformance vectors, and its author wants adapters
for Textual, Bubble Tea and Ink. Those are concrete openings. Nevertheless,
Taria is not a screen-reader implementation, and
[Textual already has a headless testing interface](https://textual.textualize.io/guide/testing/).
I have not established the additional users, capability or scope needed to
defend a great-work proposal. A new generic semantic-terminal layer would
repeat existing work. An adapter may be useful; this round did not qualify it.

## Collaborative document structure

[Peritext](https://www.inkandswitch.com/peritext/) supplies a model for merging
inline formatting and identifies structural extensions as future work. That
older statement must be read alongside current
[Automerge rich text](https://automerge.org/docs/reference/documents/rich-text/),
its [schema](https://automerge.org/docs/reference/under-the-hood/rich-text-schema/),
and [Loro's movable-tree implementation](https://www.loro.dev/blog/movable-tree).
These already provide substantial structural machinery.

The [ProseMirror table-growth report](https://github.com/ProseMirror/prosemirror-tables/issues/249)
contains a concrete concurrent row/column failure, but was closed as completed
in January 2026. [Current y-prosemirror caveats](https://raw.githubusercontent.com/yjs/y-prosemirror/master/CAVEATS.md)
describe structural limitations and planned mitigation. I did not reproduce
a current failure or finish comparison with the newer spreadsheet literature;
the full text of AegisSheet (DOI 10.1145/3806077.3806695) was inaccessible through
the reader. This is unresolved prior art, not evidence of novelty.

## What would change this verdict

A later proposal should bring one named capability, its nearest current
implementation and a discriminating comparison. For example: a cross-library
ownership failure not caught by the existing suites, a requested adapter used
by a real application with a justified scope, or a current structural merge
failure with precise intended semantics. No build or fresh research task is
queued here. These leads do not yet earn the house's weeks.
