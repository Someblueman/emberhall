## Reproduced boundary (primary): Unicode NFC/NFD rename on APFS

Untested by the suite (suite covers `snow` snowman round-trip and `new\nline` /
`a:b` / `back\slash` rejection, but no normalization pair, no rename of an
equivalence form). Real CLI probes (temporary dirs only, no protected bytes):

- Created `café.txt` NFC (`U+0063 U+0061 U+0066 U+00E9 ...`, bytes
  `b'caf\xc3\xa9.txt'`). `create` exit 0; manifest path is NFC.
- On this APFS volume, creating the NFD form (`cafe + U+0301`, bytes
  `b'cafe\xcc\x81.txt'`) with `O_EXCL` fails `FileExistsError [Errno 17]`:
  NFC and NFD cannot coexist — APFS treats them as the same name.
- Byte rename NFC to NFD via `os.rename` succeeds and changes stored bytes to
  `b'cafe\xcc\x81.txt'`; `os.listdir` then returns NFD codepoints. APFS
  lookup is insensitive: after the rename, opening via **either** NFC or
  NFD name succeeds and reads the same bytes.
- `verify` (NFD backup vs NFC manifest) exit 1:
  `{"changed": [], "extra": ["cafe\u0301.txt"], "matched": 0, "missing": ["caf\u00e9.txt"], "ok": false}`.
  Reverse direction (NFC backup vs NFD manifest) is symmetric exit 1.
- Creation via NFD string stores NFD bytes (no OS normalization to NFC);
  inventory faithfully records whichever form was created.

Assessment: this is byte-exact v1 behavior, not a defect. Blackout compares
exact UTF-8 path strings, matching Git/POSIX semantics where NFC and NFD
can be two distinct files on Linux ext4. Normalizing would conflate those
distinct files. APFS-insensitive lookup (either name opens the file) does
not imply a manifest match — restore must preserve exact bytes. No code
change warranted here; a README clarification of the normalization policy
is left for canonical integration, not done in this bounded trial.
